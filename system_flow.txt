PLAYTO PAYOUT ENGINE - COMPLETE SYSTEM FLOW

Here is the entire flow of the application explained in simple, non-jargon language. 

---

### 1. The Foundation: The Immutable Ledger
Instead of saving a merchant's balance as a single number (like `balance = 500`), the system uses a "Ledger" (the `Transaction` table). 
Think of it like a bank statement. If you want to know the merchant's balance, the database simply adds up all the money that came in (`CREDIT`) and subtracts all the money that went out (`DEBIT`). 
Because we never store a single balance number, it is impossible for the balance to accidentally go out of sync or drift due to a bug. The ledger is the absolute source of truth.

### 2. Requesting a Payout (The API)
When a merchant clicks "Withdraw Funds" on the React dashboard, here is exactly what happens:

- **The Queue (Row-Level Locking):** The backend receives the request and immediately places a "lock" on the merchant's database row (`select_for_update`). If two payout requests arrive at the exact same millisecond, the lock forces them into a single-file line. Request B must wait for Request A to finish completely before it is allowed to touch the merchant's data. This guarantees the merchant can never overdraw their account.
- **Idempotency Check:** While the lock is active, the system checks if it has seen this exact request before (using a unique `Idempotency-Key` sent by the frontend). If it has, it means the user accidentally double-clicked or the network glitched. The system safely ignores the duplicate and just returns the original response.
- **Holding the Funds:** The system recalculates the balance to ensure there are enough funds. It then creates a `Payout` record marked as `PENDING`. Crucially, it instantly creates a `DEBIT` transaction in the ledger. This deducts the money from the merchant's available balance so it cannot be spent anywhere else. The funds are now "held".

### 3. Processing the Payout (The Background Worker)
Moving money takes time, so we don't make the user wait on a loading screen. We hand the job off to a background worker (Celery).

- The Celery worker picks up the `PENDING` payout and changes its status to `PROCESSING`.
- It simulates talking to an international bank. It waits for a second, then rolls a pair of virtual dice:
    - **70% Chance (Success):** The payout status changes to `COMPLETED`. The money is officially gone.
    - **20% Chance (Failure):** The bank rejects the transfer. The payout is marked as `FAILED`. The system automatically creates a `CREDIT` transaction to refund the held money back to the merchant's available balance.
    - **10% Chance (Hang):** The network drops. The worker crashes or stops responding, leaving the payout stuck in `PROCESSING`.

### 4. Rescuing Stuck Payouts (The Sweeper)
Because networks are unreliable, the 10% "Hang" scenario is a reality. To fix this, we have a separate automated janitor (Celery Beat).

- Every 30 seconds, this janitor sweeps the database looking for any payouts that have been stuck in `PROCESSING` for too long.
- When it finds one, it tells the system to try again (`retry_stuck_payout_task`). 
- It will try up to 3 times, waiting a little longer between each attempt (exponential backoff: 2s, 4s, 8s). 
- If it still fails after 3 tries, it throws in the towel, marks the payout as `FAILED`, and refunds the merchant's money.

### 5. The React Dashboard
While all of this complex locking, background processing, and sweeping is happening on the backend, the frontend makes it look effortless to the user.

- The React app uses a technique called "polling". Every 2 seconds, it silently asks the backend, "Hey, any updates?"
- It fetches the latest calculated balance, the held balance, and the status of all payouts.
- Because of this polling, when the Celery worker finally completes a payout or issues a refund in the background, the UI on the merchant's screen updates in real-time automatically—no page refresh required. 
- The user also added a smooth dropdown that allows you to switch between different seeded merchants ("Acme Corp" and "Globex Inc") to view their independent ledgers and request payouts on their behalf.
